AWS SAA演習問題まとめ

このページは、チャット内で確認したAWS問題をまとめたもの。
正解、理由、重要用語、試験での見分け方を整理している。

1. LambdaからRDSへ安全に接続する認証情報管理

問題の要点

AWS Lambdaで開発しているアプリケーションが、Amazon RDSに保存されたデータを使用する。
Lambda関数からRDSへアクセスする際に、RDSの認証情報を安全に保存して使いたい。

正解：AWS Systems Manager Parameter Storeに認証情報を保存し、読み取り権限を持つIAMポリシーをIAMロールに付与し、そのIAMロールをLambda関数に付与する。

理由

Lambdaは実行時にIAMロールの権限でAWSサービスへアクセスする。
そのため、Parameter Storeから認証情報を取得したい場合は、Lambda関数に付与するIAMロールに ssm:GetParameter などの権限を付与する必要がある。

重要用語

  • AWS Lambda：サーバーを管理せずにコードを実行できるサービス。
  • Amazon RDS：AWS上で使えるマネージド型リレーショナルデータベース。
  • RDSインスタンス：AWS上に作成したデータベースサーバー。
  • Parameter Store：パスワードや設定値を安全に保存する場所。
  • IAMロール：AWSサービスに付与する権限のまとまり。
  • IAMポリシー：許可・拒否する操作を定義したルール。
覚え方：
Lambda → IAMロールで動く。
IAMロール → IAMポリシーで権限を持つ。
認証情報 → Parameter Storeに保存する。

2. ActiveMQを使う既存システムをAWSへ低改修で移行

問題の要点

オンプレミスの多層Webアプリケーションが、Webサーバーとアプリケーションサーバーに分かれている。
システム間の疎結合化にApache ActiveMQを使っている。
できる限り改修せず、高可用性かつ低運用負荷でAWSへ移行したい。

正解：EC2を複数AZにまたがるAuto Scalingグループに所属させ、システム間連携にはアクティブ/スタンバイ構成のAmazon MQを利用する。

理由

既存でApache ActiveMQを使っているため、改修を少なくするならAmazon MQが適している。
Amazon MQはActiveMQやRabbitMQをマネージドで利用できるサービス。
SQSへ置き換えるとアプリケーション側の改修が大きくなる可能性がある。

重要用語

  • Apache ActiveMQ：アプリ間のメッセージを一時的に預かるメッセージブローカー。
  • Amazon MQ：ActiveMQやRabbitMQをAWSマネージドで使うサービス。
  • 疎結合：システム同士を直接強く依存させず、間にキューなどを挟んで連携する設計。
  • Auto Scaling：EC2台数を自動調整する仕組み。
  • アクティブ/スタンバイ構成：片方が稼働し、もう片方が待機する冗長構成。
覚え方：
既存ActiveMQをなるべく変えずに移行 → Amazon MQ。
AWSネイティブに作り直すならSQSも候補だけど、今回は「改修少なく」が重要。

3. CloudWatch LogsのログをOpenSearchへリアルタイム連携

問題の要点

Eコマース企業がWebサイトのユーザーアクティビティをCloudWatch Logsに保存している。
高度な検索と分析のために、Amazon OpenSearch Serviceへリアルタイムで保存したい。

正解：CloudWatch Logsのサブスクリプションフィルターを使用して、データをOpenSearch Serviceへストリーミングする。

理由

CloudWatch Logsのサブスクリプションフィルターを使うと、ロググループに入ってきたログイベントを ほぼリアルタイムで別サービスへ送信できる。
OpenSearchへログを流し、高速検索・分析・可視化に使える。

重要用語

  • CloudWatch Logs：AWSのログ保存・監視サービス。
  • Amazon OpenSearch Service：大量ログやテキストデータを高速検索・分析するサービス。
  • サブスクリプションフィルター：CloudWatch Logsのログをリアルタイムに別サービスへ送る仕組み。
  • ストリーミング：データを溜めてからではなく、流れてきた順に処理する方式。
覚え方：
CloudWatch Logs → OpenSearchへリアルタイム転送
→ サブスクリプションフィルター。

4. 既存EC2 500台へCloudWatchエージェントを効率的に導入

問題の要点

メディア制作会社が、ビデオエンコード用EC2 Linuxインスタンスの詳細メトリクスを監視したい。
約500台のEC2があり、設定や用途は異なる。
すべてにCloudWatchエージェントを効率的にインストールしたい。

正解：AWS Systems Manager Run Commandを使用して、すべてのEC2インスタンスにCloudWatchエージェントをインストールする。

理由

既存の多数のEC2に対して一括でコマンドを実行したい場合、Systems Manager Run Commandが適している。
1台ずつSSHして作業する必要がなく、CloudWatchエージェントの導入をまとめて実行できる。

重要用語

  • CloudWatchエージェント：EC2のメモリ使用率、ディスク使用率など詳細メトリクスを収集するエージェント。
  • AWS Systems Manager：EC2などの運用管理を行うサービス群。
  • Run Command：EC2へログインせず、複数台に一括でコマンドを実行する機能。
  • SSM Agent：Systems ManagerからEC2を操作するために必要なエージェント。
覚え方：
既存の大量EC2に何かを入れる・実行する
→ Systems Manager Run Command。

5. センサー・ドローンデータのリアルタイム収集と異常検知

問題の要点

農業関連企業が、農場のセンサーやドローンから送られる気象データ・土壌水分情報を収集したい。
データは平均5分おきに送られる。
異常な気象や土壌状態を即座に検出し、全データをデータレイクに保存したい。

正解：Amazon Kinesis Data Streamsでデータを取り込み、Amazon Managed Service for Apache Flinkでリアルタイム分析し、分析後データをAmazon S3に保存する。

理由

リアルタイムに流れてくるデータを取り込むにはKinesis Data Streamsが適している。
そのストリーミングデータをリアルタイムに分析・異常検知するにはManaged Service for Apache Flinkが適している。
データレイクとして保存する先はS3。

重要用語

  • Amazon Kinesis Data Streams：リアルタイムに流れる大量データを取り込むサービス。
  • Amazon Managed Service for Apache Flink：ストリーミングデータをリアルタイム分析するマネージドサービス。
  • Amazon S3：オブジェクトストレージ。データレイクの保存先としてよく使われる。
  • データレイク：生データや加工済みデータをまとめて保存する大規模データ保管場所。
  • リアルタイム分析：データが到着したタイミングで即座に分析すること。
覚え方：
流れてくるデータを受ける → Kinesis Data Streams。
流れてくるデータを分析する → Managed Service for Apache Flink。
データレイク → S3。

6. KMSキーの誤削除防止と管理者通知

問題の要点

アプリケーションデータがKMSのカスタマーマネージドキーで暗号化されている。
運用者が誤ってキーを削除しようとした場合、削除を防止し、管理者へメール通知したい。
運用オーバーヘッドは最小限にしたい。

正解：Systems Manager Automationでキー削除をキャンセルするランブックを設定し、EventBridgeルールでキー削除操作をトリガーにランブック実行とSNS通知を行う。

理由

KMSキーは削除操作後すぐに消えるのではなく、削除予定状態になる。
そのため、削除操作をEventBridgeで検知し、Systems Manager Automationのランブックで CancelKeyDeletion を実行すれば削除をキャンセルできる。
管理者へのメール通知にはSNSを使う。

重要用語

  • AWS KMS：暗号化キーを作成・管理するサービス。
  • カスタマーマネージドキー：ユーザー側で管理できるKMSキー。
  • ScheduleKeyDeletion：KMSキーを削除予定にする操作。
  • CancelKeyDeletion：KMSキーの削除予定をキャンセルする操作。
  • EventBridge：AWS上のイベントを検知し、別サービスへ連携するサービス。
  • Systems Manager Automation：定型運用作業を自動実行する機能。
  • ランブック：運用手順を自動実行できる形にしたもの。
  • SNS：通知を配信するサービス。メール通知などに使う。
覚え方：
KMSキー削除を検知 → EventBridge。
削除を止める → CancelKeyDeletion。
自動実行 → Systems Manager Automation。
メール通知 → SNS。

7. S3上のCSVアクセスログを低運用でSQL分析

問題の要点

メディア企業がWebサーバーのアクセスログをS3バケットに保存している。
アクセスログは1分ごとにCSV形式でアップロードされ、1日の合計データ量は数百MB。
サイト別・時間帯別のアクセス傾向を速やかに把握したい。
開発・運用工数を最小限にしたい。

正解：AWS GlueクローラーでS3バケット内のアクセスログファイルをカタログ化し、Glue Data Catalogに登録されたテーブル定義を利用して、Amazon AthenaでSQLクエリを実行する。

理由

S3に保存されたCSVやログを、少ない運用工数でSQL分析したい場合はAthenaが適している。
GlueクローラーでCSVの構造を調べ、Glue Data Catalogにテーブル定義を登録する。
Athenaはそのテーブル定義を使って、S3上のデータに直接SQLを実行できる。

重要用語

  • Amazon S3：ファイルやログを保存するオブジェクトストレージ。
  • S3バケット：S3内に作るデータの入れ物。
  • CSV：カンマ区切りの表形式ファイル。
  • アクセスログ：Webサイトへのアクセス履歴を記録したファイル。
  • AWS Glue：データ分析の準備や変換を行うサービス。
  • AWS Glueクローラー：S3などを巡回し、データ構造を自動検出してカタログ化する機能。
  • AWS Glue Data Catalog：データの場所・列名・型などを管理するメタデータカタログ。
  • テーブル定義：S3上のファイルを表として扱うための設計情報。
  • Amazon Athena：S3上のデータをSQLで直接分析できるサーバーレスサービス。
  • SQLクエリ：データ検索・集計を行うSQL文。

全体像

Webサーバー
  ↓ アクセスログCSVを1分ごとに出力
Amazon S3バケット
  ↓
AWS Glueクローラーが中身を調べる
  ↓
AWS Glue Data Catalogにテーブル定義を登録
  ↓
Amazon Athenaがテーブル定義を使う
  ↓
SQLでS3上のログを分析
覚え方：
S3上のCSVやログを手軽にSQL分析
→ Glueクローラー + Glue Data Catalog + Athena。

8. AWS移行時のWindowsサーバー管理とDirectory Service

問題の要点

オンプレミスで複数のWindowsサーバーによるWebアプリケーションを運用している。
各WindowsサーバーはMicrosoft Active Directory（AD）で管理されている。
WebアプリケーションをAWSへ移行し、Windowsサーバー群をEC2 Windowsインスタンスに切り替える。
オンプレミスのADは、このWebアプリケーション用Windowsサーバー群のみを管理している。
運用負荷を最小限にしたい。

正解：AWS Directory Serviceを作成してWindowsインスタンス群を管理する。

理由

オンプレミスADが他の社内システム全体を管理しているなら、オンプレAD連携を考える。
しかし今回のオンプレADは、移行対象のWindowsサーバー群だけを管理している。
そのためAWS側にDirectory Serviceを用意し、Windows EC2をそこで管理する方が運用負荷を抑えやすい。

不正解の理由

  • Windowsインスタンスの1台にADを導入する：自前管理になる。冗長化、バックアップ、パッチ、障害対応が必要。
  • オンプレADと連携するDirectory Service：既存ADを残す必要がある場合は有効。ただし今回はオンプレADを残す理由が薄い。
  • AD用EC2を作成する：構築はできるが、ADサーバーの運用負荷が増える。
覚え方：
Windows管理の中心 → AD。
AWS上でAD管理を楽に使う → AWS Directory Service。
既存オンプレADを残したい → AD ConnectorやManaged Microsoft ADとの連携を検討。
今回はオンプレADを残す理由が弱いので、AWS側で管理する。

9. DR用に別リージョンへ同じアーキテクチャを構築

問題の要点

業務システムの運用環境をアジアのリージョンで稼働している。
災害復旧（DR）のため、北米リージョンに現在と同じアーキテクチャを迅速かつ確実に構築したい。

正解：現行インフラを元にCloudFormationテンプレートを作成し、北米リージョンに適用する。

理由

「同じ構成を迅速かつ確実に再現したい」はInfrastructure as Codeの要件。
CloudFormationを使うことで、VPC、サブネット、EC2、ALB、RDS、Security Groupなどをコードとして再現できる。

不正解の理由

  • Elastic Beanstalk：アプリ実行環境向け。インフラ全体のDR構成再現には弱い。
  • AWS Backup：データ復旧向け。アーキテクチャ全体を作るものではない。
  • AWS Config：構成記録・監査向け。手動構築になるため、迅速・確実とは言いにくい。
覚え方：
同じ構成を別リージョンに再現 → CloudFormation。
データを戻す → AWS Backup。
設定履歴を見る → AWS Config。

10. 複数アカウント・複数VPCのECSマイクロサービス間通信

問題の要点

動画配信プラットフォームがECS上の複数マイクロサービスで構成されている。
各マイクロサービスは独立チームにより複数AWSアカウントで運用されている。
gRPCによるサービス間通信とサービスディスカバリーが必要。
管理負担を最小限にしたい。

正解：VPC Latticeでサービスネットワークを構築し、各マイクロサービスと通信が必要なVPCを関連付ける。

理由

VPC Latticeは、複数VPC・複数アカウントにまたがるサービス間通信をサービス単位で管理できる。
ECSタスクをターゲットとして登録でき、gRPCやサービスディスカバリー、アクセス制御にも対応しやすい。

不正解の理由

  • VPCピアリング：VPC同士を直接接続する方式。数が増えるとルートやセキュリティ管理が複雑。
  • Direct Connect：主にオンプレミスとAWSを専用線で接続するサービス。今回の主題ではない。
  • Transit Gateway：複数VPC接続のハブにはなるが、サービス単位の検出や制御はVPC Latticeの方が適切。
覚え方：
VPC同士をつなぐ → VPC Peering / Transit Gateway。
サービス同士をつなぐ → VPC Lattice。
オンプレとAWSを専用線でつなぐ → Direct Connect。

11. オンプレVMを短期間・低ダウンタイムでAWSへ移行

問題の要点

オンプレミスのデータセンター内で複数VMを使い、販売管理システムを運用している。
コスト最適化のためAWS移行を検討。
まずはビジネス影響が少ないバッチ処理系ワークロードを対象にする。
コードや構成変更を最小限にし、短期間で移行し、ダウンタイムも最小限にしたい。
3つ選択。

正解：(3) Application Migration Service用にAWS Replication Agentをインストールする、(5) 初期レプリケーション後にテストインスタンスを起動する、(6) カットオーバー時に書き込みを停止し、カットオーバーインスタンスを起動して最終同期する。

理由

オンプレVMをコード変更少なくEC2へ移行するなら、AWS Application Migration Service（MGN）が適している。
移行元VMにAWS Replication Agentを入れ、継続レプリケーションを行う。
初期同期後にテスト起動し、本番切替時に書き込みを止めて最終同期し、AWS側へカットオーバーする。

不正解の理由

  • DataSyncでディスクイメージをS3へコピー：DataSyncはファイル転送向け。VM丸ごとの低ダウンタイム移行にはMGNの方が適切。
  • Elastic Disaster Recovery：DR用途。今回の主目的は移行。
  • Systems Manager Patch Manager：パッチ管理向け。移行手順ではない。
覚え方：
オンプレVMをそのままEC2へ移したい → Application Migration Service。
災害対策として待機環境を作りたい → Elastic Disaster Recovery。
カットオーバー → 「今日から新環境を本番にします」の切替。

12. DynamoDBを過去36時間以内の任意時点に戻す

問題の要点

顧客のセッション情報とリアルタイム使用履歴をDynamoDBに保存している。
データは頻繁に更新されている。
誤操作やバグによる削除・変更があっても、過去36時間以内の任意時点に戻したい。
運用負荷を最小限にしたい。

正解：DynamoDBテーブルでポイントインタイムリカバリ（PITR）を有効化する。

理由

DynamoDBのPITRは、テーブルを過去の任意時点に復元するための機能。
定期バックアップを自作しなくても、誤操作やバグによる更新から復旧できる。

不正解の理由

  • EventBridgeで30分ごとにS3エクスポート：30分単位では任意時点に戻せない。運用も増える。
  • AWS Backupのスナップショット：バックアップ取得時点への復元。任意時点復元ならPITRが適切。
  • DynamoDB Streams + Lambda + Firehose + Redshift：変更データの連携・分析向け。テーブル復元用途ではない。
覚え方：
DynamoDBを任意時点に戻したい → PITR。
定期バックアップ → AWS Backup。
変更イベントを拾う → DynamoDB Streams。

13. EKS上の複数マイクロサービスをHTTPSのURIパスで振り分け

問題の要点

輸送管理システムがEKS上の複数マイクロサービスで動作している。
外部取引先がインターネット経由でHTTPS接続する。
URIパスに応じて、経路計算API、集荷依頼API、請求照会APIなどへ振り分けたい。
サービスが増えても外部エンドポイントを増やさず、一貫したアクセスを提供したい。

正解：EKSクラスターにAWS Load Balancer Controllerを導入し、ALBを自動プロビジョニングしてURIパスに基づいてルーティングする。

理由

URIパスに基づく振り分けはHTTP/HTTPSの中身を見るL7ルーティング。
ALBはパスベースルーティングに対応している。
EKSではAWS Load Balancer ControllerがKubernetesのIngress定義を見て、AWS側のALBやルールを自動作成・更新してくれる。

不正解の理由

  • CloudFront：CDNやキャッシュが主目的。EKS内のAPI振り分けの本命ではない。
  • NLB：L4ロードバランサー。基本的にURIパスを見た振り分けはできない。
  • API Gateway + Lambda転送：実装・運用が増える。今回の要件ではALBが自然。
覚え方：
URLパスで振り分け → ALB。
TCP/UDPで高速転送 → NLB。
EKSのIngressからALB/NLBを自動作成 → AWS Load Balancer Controller。
EKSはAWSでKubernetesを使うためのサービス。

14. 既存Javaアプリを迅速にコンテナ化してFargateへ移行

問題の要点

オンプレミスでJavaアプリケーションを運用している。
迅速にコンテナ化してAWSへ移行したい。
インフラ管理の負担を最小限にし、CloudWatchメトリクスに基づく自動スケーリングを実現したい。

正解：AWS App2Containerを使用してアプリケーションをコンテナ化し、CloudFormationテンプレートを利用してAWS Fargateにデプロイする。

理由

App2Containerは、既存のJava/.NETアプリケーションを解析し、コンテナ化やECS/EKS向けのデプロイ設定作成を支援するツール。
Fargateを使えば、コンテナを動かすサーバー管理をAWSに任せられる。
CloudWatchメトリクスに基づくオートスケーリングも実現しやすい。

不正解の理由

  • Elastic Beanstalk：Javaアプリのデプロイには使えるが、今回の主眼である迅速なコンテナ化とはずれる。
  • Application Migration Service：サーバーごとEC2へリフトアンドシフトする移行向け。コンテナ化ではない。
  • EKS + HPA：Kubernetes運用が必要になり、インフラ管理負荷が増えやすい。
覚え方：
既存Java/.NETアプリをコンテナ化 → App2Container。
VMをそのままEC2へ移行 → Application Migration Service。
サーバー管理なしでコンテナ実行 → Fargate。

15. VPCのIPアドレス不足を既存環境への影響少なく解消

問題の要点

172.16.20.0/24のCIDRブロックで構成されたVPCを使っている。
新しいマイクロサービスやバッチ処理用インスタンスが増え、プライベートIPアドレスが不足しそう。
既存環境への影響を最小限にし、運用オーバーヘッドも抑えたい。

正解：VPCに172.16.21.0/24のセカンダリCIDRブロックを追加する。

理由

VPCの既存CIDRは直接拡張できない。
しかし、VPCにはセカンダリCIDRブロックを追加できる。
追加したCIDRから新しいサブネットを作成すれば、既存VPCを作り直さずにIPアドレス空間を増やせる。

不正解の理由

  • 新しいVPCを作成して移行：影響が大きい。ルート、SG、ALB、DNSなどの再設計が必要。
  • 新しいサブネットを追加：既存CIDR内に空きがない場合、根本解決にならない。
  • 既存CIDRを/16へ変更：VPCの既存CIDRブロックは直接変更できない。
覚え方：
VPCのIPが足りない → セカンダリCIDRを追加。
サブネットはVPCのCIDRから切り出すだけ。
冷蔵庫の棚を増やしても容量は増えない。容量を増やすにはCIDR追加。

16. Kubernetesを活用しつつインフラ管理を最小化

問題の要点

コンテナ化されたアプリケーションをAWS上で大規模にデプロイしたい。
オープンソースのKubernetesを積極的に活用したい。
インフラ管理の負担を最小限にし、開発チームがアプリ開発に集中できる環境にしたい。

正解：Amazon EKSクラスターにアプリケーションをデプロイし、EKS Auto Modeを使用する。

理由

Kubernetesを使いたいならEKSが候補。
さらにインフラ管理の負担を最小限にするなら、EKS Auto Modeが最も合う。
EKS Auto Modeは、コンピュート、スケーリング、コアアドオン、ロードバランシング、ストレージ連携などの運用負荷を減らす方向の機能。

不正解の理由

  • ECS + Fargate：運用負荷は小さいがKubernetesではない。
  • EKSマネージドノードグループ：Kubernetesは使えるが、ノードグループの設計・更新・容量管理が残る。
  • セルフマネージドKubernetes：自由度は高いが、運用負荷が最大。
覚え方：
Kubernetesを使いたい + 運用負荷を最小化 → EKS Auto Mode。
Kubernetes不要 + コンテナを楽に動かす → ECS Fargate。
Kubernetesを全部自分で管理 → セルフマネージドKubernetes。

17. ACMにインポートした外部証明書の期限接近をメール通知

問題の要点

セキュリティ標準により、SSL/TLS証明書は指定された外部認証局から取得している。
その証明書をACMにインポートし、インターネット向けWebアプリケーションで利用している。
インポート証明書の有効期限切れを防ぐため、有効期限が近づいたらメール通知したい。
SNSトピックは作成済みで、担当者メールアドレスも購読済み。
既存SQSキューもあるが、運用負荷は抑えたい。

正解：EventBridgeでACM Certificate Approaching Expirationイベントタイプを対象とするルールを作成し、SNSトピックをターゲットに設定する。

理由

インポート証明書はACMが自動更新してくれない。
そのため、有効期限接近イベントをEventBridgeで検知し、SNSへ通知するのが適切。
SNSトピックにメール購読があるため、LambdaやSQSを挟む必要はない。

不正解の理由

  • ACMの自動更新：ACM発行証明書なら自動更新できるが、外部CAから取得してインポートした証明書は自動更新されない。
  • Certificate Expiredイベント：期限切れ後では遅い。要件は期限が近づいた時点の通知。
  • Lambda経由でSNS通知：直接SNSに送れるため余計な運用が増える。
  • SQSターゲット：キューに入るだけでメール通知されない。処理するコンシューマが別途必要。
覚え方：
ACMインポート証明書は自動更新されない。
期限接近 → EventBridge。
メール通知 → SNS。
SQSは「後で処理するための行列」であって通知先ではない。
